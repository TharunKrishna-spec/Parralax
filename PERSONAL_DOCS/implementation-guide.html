Implementation Guide

Predictive Self-Healing IoT Mesh
with Real-Time Anomaly Detection

A combined hardware-and-software build guide for a 5-node ESP32 mesh that predicts a failing wireless link from RSSI trend and packet delivery, reroutes traffic before a heartbeat timeout fires, and flags anomalous sensor readings on-device with no cloud step and no pre-training.

5× ESP32-WROOM-32 · ESP-NOW · Arduino core 3.x 2 analog sensors / node MAD Z-score + flatline anomaly engine Distance-vector + priority override routing
01

System Architecture

Seven layers, bottom to top: raw radio, statistics, routing decisions, reliability, and reporting. Read this once before touching a breadboard or an .ino file — every later section refers back to it.

Node topology

Five roles: A (source), B and C→D (two relay paths of different quality), S (sink/root). The direct A–S link is deliberately weak and long so it stays the fewest-hop path without being the best-quality one — this is what makes the priority override visibly different from normal routing.

Demo behaviour this topology produces Drop a Faraday bag over Node B → link score falls → mesh reroutes A→C→D→S (prefers the strong 3-hop path over the weak 1-hop direct link). Send a priority packet → it ignores link quality and forces the weak direct A→S hop instead — the two traffic classes visibly diverge on the dashboard.

Hardware & Pin Connections

Every node shares one wiring pattern. Two nodes (S and C) add an OLED on top of it. Wire all five identically first, then add the two displays.

The single most likely "sensor is lying" bug On the classic ESP32, ADC2 pins stop working the moment ESP-NOW/WiFi is active — any analogRead() on an ADC2 pin returns an error or garbage, and this only appears after the radio starts, so it will not show up in a quick pre-mesh bench test. Wire both analog sensors on every node to ADC1 pins only.

Software & Control Flow

Same five boards, same firmware image (role is selected by a compile-time flag or a MAC-address lookup table). Four flowcharts cover everything that runs: boot, the main loop, the link predictor, and the anomaly engine.

Toolchain constraint — confirm this at hour 0, not hour 10 Per-packet RSSI is only exposed in the ESP-NOW receive callback on Arduino-ESP32 core 3.x (ESP-IDF ≥ 5.1), where the callback's first argument is esp_now_recv_info_t* and RSSI is read from info→rx_ctrl→rssi. On core 2.x the callback gives only the MAC address — no RSSI — and the entire predictor depends on this one fact. Pin the toolchain to core 3.x before writing any predictor code, and do not copy pre-3.0 tutorials; several fail to compile on 3.0.0.

Algorithms Reference

The four pieces of logic that make this project defensible: link prediction, robust anomaly detection, stuck-value detection, and priority override. Each has a diagram and reference pseudocode.

5.1 — Link degradation predictor

RSSI alone is sampled only during the packet preamble and often stays flat even as real interference builds — predicting failure from raw RSSI risks missing the exact degradation it's meant to catch. The fix: smooth first, then differentiate, then fuse with delivery rate.

// smoothing: HIGHER alpha = more reactive, lower = smoother
rssi_ewma = alpha * rssi_sample + (1 - alpha) * rssi_ewma;   // alpha ~ 0.3

// slope: least-squares fit over the last W points of rssi_ewma, NOT raw rssi
slope = least_squares_slope(rssi_ewma_window, W);             // negative = degrading

// degrade_term is zero unless the trend is genuinely falling
degrade_term = clamp(-slope / SLOPE_REF, 0.0, 1.0);

link_score = w1 * (1.0 - degrade_term) + w2 * pdr;   // w1 = w2 = 0.5

if (link_score < THRESHOLD) {
  below_count++;
  if (below_count >= 3) trigger_proactive_reroute();
} else {
  below_count = 0;
}
// heartbeat timeout stays armed regardless, as a hard fallback

Timing parameters — pin these first

ParameterStarting valueWhy
Heartbeat interval100–200 msGives the slope estimator resolution — 1 Hz is far too slow to beat a timeout.
Slope window W15–20 samples (≈2–4 s)Enough to see a trend without lagging the event.
PDR window20 framesMatches ≈2–4 s at the heartbeat rate above.
Heartbeat timeout3–5× predictor reaction (≈1–2 s)Guarantees the proactive reroute normally wins; timeout is only a safety net.

5.2 — Anomaly engine: MAD Z-score + flatline detector

A standard Z-score is undermined by the anomaly it's meant to catch: one extreme reading drags the mean and inflates the standard deviation, hiding the spike. The modified Z-score uses the median and the median absolute deviation (MAD) instead — both are robust to outliers by construction. A point-anomaly test like this, however, structurally cannot see a sensor stuck at its own median — that needs a second, independent detector.

// ---- boot calibration: run once, ~100 samples, per sensor ----
median = median(boot_samples);
mad    = median(abs(boot_samples - median));
if (mad < MAD_FLOOR) mad = MAD_FLOOR;   // ~3 ADC LSB on a 12-bit ADC — real noise floor

// ---- every subsequent sample ----
float compute_modified_z(float x, float median, float mad) {
  if (mad < MAD_FLOOR) mad = MAD_FLOOR;
  return 0.6745f * fabsf(x - median) / mad;
}
// flag SPIKE/JUMP if |modified_z| > 3.5   (Iglewicz & Hoaglin threshold)

// ---- flatline detector, runs alongside, catches what MAD-Z structurally cannot ----
if (fabsf(x - last_val) < EPS) stuck_count++; else stuck_count = 0;
last_val = x;
bool stuck = (stuck_count >= STUCK_N);   // STUCK_N ~ 50 samples

5.3 — Priority override

Normal traffic takes the quality-optimal route from the distance-vector table. A priority flag on a packet skips that lookup entirely and forces the shortest-hop path, regardless of quality — visible on this topology because the shortest path (direct A–S) is deliberately the weakest one.

5.4 — Reliability layer

Runs underneath both routing modes: every forwarded frame gets a hop-by-hop ACK; a missing ACK triggers a bounded retransmit; a sequence-number-based duplicate filter drops repeats caused by retransmits or multi-path delivery. Per-hop PDR for § 5.1 comes free from the ESP-NOW send callback's success/fail status — no extra protocol needed.

Testing & Evaluation Metrics

Do not present specific numbers to judges until they've actually been logged from your own hardware — track these three live and quote real numbers on the day.

MetricDefinitionHow to instrument it
Reroute lead-timeTime between the proactive reroute and when the heartbeat timeout would have fired.Counterfactual — log the last-heartbeat timestamp, compute the timeout deadline you deliberately avoided, report deadline − reroute_time. It will not appear on its own.
Packet Recovery Ratio (PRR%)Dropped packets successfully re-delivered via an alternate route, out of total dropped.Count at the sink (Node S) — dropped-then-recovered ÷ total dropped, over a fixed test window.
Anomaly false-positive rateFalse alarms during clean operation ÷ total baseline samples.Run each node untouched for a fixed period post-calibration, count SPIKE/JUMP or STUCK flags that fired without a manual trigger.

Pre-flight checklist — before every demo run

  • All 5 nodes power on and reach the main loop within 5 seconds
  • All 5 nodes report the same WiFi channel
  • Boot calibration completes without restarting on any node
  • Node S OLED and dashboard show live link_score for the current best path
  • Node C OLED is blank/idle (no false SPIKE/JUMP or STUCK) at rest
  • A normal packet and a priority packet visibly take different routes
  • Faraday bag over Node B produces a reroute within the expected lead-time window
  • Removing the Faraday bag lets Node B rejoin the healthy path again
  • Spare board and spare jumper wires within reach

Demo Staging & Judging Script

Three minutes, three visible moments, in this order.

TimeActionWhat it demonstrates
0:00–0:30Drop the Faraday bag over Node B — no software controls touched.The interactive failure: a sudden RF attenuation drop on the primary routing node.
0:30–1:30Point to Node S's OLED / dashboard.Proactive recovery: fused RSSI-slope and PDR score detects degradation and reroutes through C and D before the heartbeat timeout expires.
1:30–2:20Twist the potentiometer on Node C sharply, then hold it dead still. Then fire a priority packet.Edge intelligence + priority override: MAD Z-score flags the spike instantly; the flatline detector catches the frozen value; a priority message forces the shortest hop while normal traffic stays on the healthy path.
2:20–3:00Sponsor framing close.Ties the demo to Nokia SON principles and Keysight's Coexistence/Continuity pillars — see § 10 wording.

Pre-empt these judge questions

QuestionAnswer
"RSSI is notoriously noisy — how can you trust it for routing?"We EWMA-smooth RSSI first, then take the slope of the smoothed signal — not the raw derivative — and fuse it with a 20-frame packet-delivery-ratio window, so a noisy-but-still-delivering link doesn't trigger a false reroute.
"A Z-score can't detect a stuck sensor — it sits at the median. How do you catch that?"Correct — that's why we run two detectors. The MAD Z-score catches spikes and jumps; a separate flatline detector counts consecutive unchanged samples to catch stuck values. Both flags are reported independently.
"Does your MAD Z-score assume a clean training phase?"Yes — boot calibration assumes reasonably stable initial conditions. We check variance during the first ~100 samples and auto-restart calibration if it's out of a safe range.
"Why an LDR alongside the potentiometer?"The pot gives a deliberate, controlled anomaly on demand. The LDR gives a real environmental disturbance — a shadow or occlusion — proving the same statistical detector generalizes across signal shapes, not just one hardcoded case.
